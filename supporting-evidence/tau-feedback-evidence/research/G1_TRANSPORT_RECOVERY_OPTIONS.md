# G1 传输中断后的恢复选择

2026-09-17｜独立方法审查；**只设计、不调用模型、不改源码或实验。** 运行状态采用根代理本次报告：G1 subscription v2 在任务 59 / replicate 29 的第二次 CLI 调用出现 WebSocket TLS handshake EOF 日志，按原 stderr 规则暂停；18 单元完成、1 单元未评分、5 单元未运行。本审查没有重新读取该次原始调用，封存统计与费用仍需执行代理核验。HTTP-only 配置的正式支持与实测由根代理另查，本报告不预先认定它已解决故障。

**推荐最小可辩护路线：选（2），封存中断的 G1 v2，另登记全部18条完成轨迹的描述性诊断审计。** 原自然收益比较结束为“未满足完整 G1 继续条件”；原 N1 的24完整单元前提也没有成立。新审计应有不同 stage、manifest 和结果目录，建议称 **N1-R1：中断运行的完成样本诊断审计**，不是降低旧门槛后的原 N1。默认不再执行剩余1＋5单元。

## 1. 先封存，不能回溯接受或改判

- 保留 v2 manifest、源码快照、STOP、原始 stderr/events/final、轨迹及全部调用账本。即便异常调用有结构完整 final 或已知 usage，也不能事后将原来严格拒收改成成功；费用按实际可知状态保留。
- 59/29 的**运行未完成、任务未评分**是基础设施状态，不是 Agent 任务失败或用户失真。已完成的18条仍分别按原始 reward、结构完整性、语义核查和用户有效性报告，不因后来的网络故障被追溯否定。
- 原 G1 明确要求完整24单元；不能凭18条已有成功或失败数量提前宣布能力门通过，也不能把未完成原因改写成“模型天花板/可修改失败不足”。目前充分的停止理由是传输中断导致本版本未完成。原 G1 规则（本地审计材料，未纳入公开包）
- 故障与模型任务能力分开，不代表传输配置无关紧要：它属于被测 CLI 系统，可能影响可运行性、耗时和成本。没有独立对照，不能断言 HTTP-only 与 v2 除连接方式外在实际模型行为上完全等价。

## 2. 三条路线比较

| 路线 | 能回答什么 | 新资源与解释代价 | 方法裁定 |
|---|---|---|---|
| **（1）HTTP-only v3 全24重新运行** | 新配置下完整目的性开发子集的可行性；全部结束且原门满足后，才考虑自然优化比较 | 新增24个完整 episode及其 actor/user/评价调用；先有配置验收和冻结。旧v2全部成本仍另列。新模型输出可变，不能保证不再中断或达到失败覆盖门。 | 若必须优先完成“同一固定配置的完整24”或继续原收益问题，这是最清楚的路径；目前不是资源最省的选择。 |
| **（2）停止 G1 自然比较，审计已有18完成轨迹** | 在明确中断所得的已完成样本中，原生诊断、可见证据支持、gate 选择与成本的描述 | 无新 acting episode；最多18次 reviewer＋36次 gate，独立复核仍最多12诊断卡。需要新登记及N1小幅版本化。不能推断全24/τ2总体率或Agent收益。 | **推荐。** 保留真实研究内容和已有投入，避免用持续换配置凑齐原实验；负结果仍可完整报告。 |
| **（3）预登记 HTTP-only 延续剩余1＋5** | 两阶段、混合配置的操作性覆盖与后续案例；不是同版24 | 新增6个完整 episode。中断的59/29须从头运行为新尝试，不能续用旧进程/环境或覆盖原记录。传输/时间与任务顺序重叠，难分辨影响。 | 若确实需要剩余任务的开发证据可以做，但不能比（2）提供更干净的统一能力结论；若随后仍要自然优化，通常还得另做完整新配置基线。当前不推荐。 |

### （1）的必要条件

新的 HTTP-only v3 独立固定全部24个原计划身份/顺序、统一配置、角色协议、官方政策、源码与预算；旧v2不是其首18条。全部任务从零状态运行，不只重跑低分或未完成任务。保留原24继续门和用户污染规则，不因为投入增加而保证最终能进入优化。报告 v2 和 v3 各自结果及合计资源，不能二选一只留下较好的成绩。

### （3）为何不能“补6条得到完整v2”

开始前登记阶段边界、原始缺失表、所有6个待运行身份与唯一新尝试，不按已经观察的分数选题。其中59/29是**明确登记的完整新尝试**，其余5条是首次尝试；都使用新的共同 HTTP-only 配置。原中断保留为单独历史尝试。

若新6条全部完成：有24个原计划身份各自可用的完成记录，来自18条v2＋6条新配置；此外仍有1条中断尝试，合计25次 episode尝试。可报告“混合两阶段方案的覆盖”，不能叫“v2完整24”、单一传输配置 benchmark 分数，或回填到旧v2的 pass^2。主表列 phase/config/attempt 映射及各自分母，合并表仅作描述。若新阶段再停，不再自动换配置滚动补齐。

## 3. 原24分母的固定报告方式

原 G1 v2 的任务台账永久保留24行，至少同时给：

| 层次 | 正确计数/口径 |
|---|---|
| 预分配运行覆盖 | 18/24完成，1/24基础设施中断未评分，5/24未运行；这不是18成功、6失败。 |
| 已完成单元的任务判定 | 令18条中已核对合格为 q、明确不合格为 f、语义或评价证据不足为 u，则 q＋f＋u＝18；保留三个数，不把 u 自动升级/删掉。最终数字由封存数据填入。 |
| 预分配观察量 | 可以给 q/24，名称必须是“24预分配单元中已观察到的合格完成比例”，不是假设所有缺失都是模型失败的能力成功率。 |
| 完成样本描述 | q/18只描述已完成样本；与q/24并列解释，不能选择更漂亮的分母替代主台账。 |
| 两次重复与 pass^2 | 原定每题两次；缺一次的题不能补0、复制第一轮或用新配置补成v2成对数据。逐题列2次/1次/0次可用；仅完整对的“两次均合格”可描述，并标明完整对数量与选择范围。v2整体完整设计的最终 pass^2 不可得。 |
| 成本 | 已完成18条＋中断59/29的全部已知CLI/input/output/时间及未知费用次数；5条未运行明确没有启动，不混成“未知成本”。既往v1/本地试点和新恢复分支另列，同时给项目累计。 |

“完成”必须以官方评价和原接受契约为准，而非文件目录存在。封存清单还应核对18条的独立语义审查是否齐全；不齐全的审查状态保留，不通过临时删除该条形成全合格样本。

## 4. 推荐路线（2）的选择偏差与研究价值

这是**停止时已经完成的运行集合的全量审计**，不是随机抽取18/24，也不是预先随机设计的自然误诊样本。固定执行顺序与停止时间决定后6条缺失；请求长度、任务交互复杂度、服务负载可能共同影响完成概率，现有证据不足以认定缺失完全随机。某些任务只有一次、另一些已有两次，必须保留 task/replicate/顺序，不能把所有诊断或重复当作独立任务扩大样本量。

入选规则只能是“截至固定停止点，按原v2规则已完成官方评价的全部单元”，不能排除失败、用户 violated/unknown、不容易定位的对话或没有诊断的例子。六条不进入完整诊断审计的原因是缺少完整轨迹/尚未运行，不是判定它们没有错误。中断轨迹可保留为基础设施附录，不作完整任务的 reviewer/gate 语义样本。

新审计计划是在知道 G1 已有成绩后制定，须明确这一点；可在**产生新 reviewer/gate 输出之前**前瞻锁定后处理问题、来源集合、抽样与标签流程。不能将其称作原 G1 实验前预注册的次要终点。

有价值的产物是：18条真实交互的来源与结束状态；原生 reviewer 的完整性/来源分布；至多每条两卡的可见性与责任支持核查；gate 对支持、反驳和信息不足建议的取舍；调用成本及失败保留。这与已有 E0–E3、评分完整性发现、真实模型通路和严格中断治理可以组成完整且可审查的研究项目。论文问题应收窄为**反馈证据可靠性与受限系统下的诊断审计**，而非仍写“已验证策略提升”。

新 reviewer/gate 可以在经独立验收的新 HTTP-only 配置上统一后处理旧v2轨迹，但必须同时记录“轨迹生成配置v2”和“诊断生成配置新版本”。这不是把两种传输混成一个 acting benchmark；它是对固定历史样本的一致再评审。配置验收失败则不启动审计，不能以方法建议替代运行证据。

## 5. N1-R1 的最小显式版本化

当前 `src/tau_feedback/n1_audit.py` 硬性要求原24身份全等、24条完整review和固定24分母；这对原 N1 正确。**不要把所有24常量改成18，或伪造六份空simulation来运行旧入口。** 新版本可复用现有组件，但需独立 stage 和审查：

1. **新 manifest 身份。** 例如 `stage=N1_interrupted_cohort_audit`、唯一 `manifest_id`；绑定原G1 v2 manifest/digest、STOP及终局台账哈希、明确故障截止点。原 N1 草案保留为未满足条件/未执行，不改日期或假称已按原门获准。
2. **总体与可审集合分开。** 保留 `parent_population_count=24` 和原24顺序/身份；新增 `eligible_review_count=18`、18个可审身份有序子序列，以及对其余6条的逐项 `infrastructure_interrupted`/`not_run`处置表。代码从冻结终局状态核对恰好全部18完成条目，不能相信手填18名单，更不能允许漏掉已完成失败。
3. **来源、分类完整绑定。** 对18条强制校验原 episode request/trajectory/calls/simulation/outcome、client预算与语义审查文件的必需哈希；对中断和未运行项采用各自真实来源，不要求不存在的simulation。分类/用户有效性来自冻结审查，不能仅由 manifest 任意填写。若完成条目存在 `qualified=unknown`，新 schema 必须保留，不能为适配旧 `qualified_pass|explicit_fail` 二选一而编造失败。
4. **审阅分母与抽样。** 全18条各最多1次reviewer，有效结果再按原固定hash规则各取最多2条agent诊断；unknown计数null，空池计数0。独立样本仍最多12张卡。互斥层建议为：用户violated/unknown优先；其余合格完成；其余完整但非合格（明确失败与unknown字段继续分开）。每层先最多4张，再hash补足；不够12不补造。该样本不能给全24或总体“准确率”。
5. **顺序和准入不减弱。** 全18reviewer完成 → 锁定pool与样本 → 输出匿名行动时证据包 → 独立首轮标签/裁决及哈希锁 → gate。`selection.json`的宿主分层/G1标签仍不得交给复核者当遮蔽包。原始unknown、定位失败、首轮分歧与结构弃权规则继续保留。
6. **预算与结果目录。** 各eligible单元继续用review cap1、gate cap2的独立账本，合计最多54次新CLI；独立全角色token/墙钟上限在首次调用前冻结。新模型/传输/源码使用新哈希和结果目录，原v2停止目录只读。新输出同时给24总体处置、18审阅覆盖和卡片分母；中断失败/未知费用不免费、不自动重试。
7. **有界契约测试。** 在假数据上验证：可审18必须精确等于冻结完成集；删掉已完成失败会拒绝；把未完成/未运行伪装完成会拒绝；24总体分母不随review池缩小；qualified unknown能进入合适层而不被改判；原先24版本仍按原规则工作；标签锁、输入绑定和1＋2预算继续成立。源代码通过审查后才登记执行。

不必为本路线新建另一套完整 backend。只需要经根代理核验的统一传输配置、原有review/gate调用桥及上述明确的队列/分母差异。已有N1测试通过不能自动证明新18集合版本正确。

## 6. 是否执行剩余1＋5，以及项目何时可结束

**推荐不执行。** 该6条既不能修复已中断v2，也不是完成18条描述性诊断审计所需输入；新增真实对话的费用高于只对现有证据作后处理。只有当用户明确选择重新优先完成统一配置24基线时走（1）；只有当确实需要缺失题目的开发案例且接受混合配置限制时另登记（3）。不得把“项目还没有正结果”作为继续采样的理由。

推荐项目完成条件：原v2停止事实及24行台账封存；E0–E3与真实试跑证据核验；若新后处理通路通过验收，完成或按预算/异常规则诚实停止N1-R1，并给逐例标签、计数、成本与来源；整理可公开的代码、版本/依赖、脱敏结果及失败边界。没有误诊、gate无增益、诊断普遍不确定或后处理再次中断，都允许形成真实结论。C1压力研究和真实GEPA可以另列有条件后续，**不是为了使结论好看而必须追加的完成条件**。

这条路线能完成一个证据边界清楚的项目，但明确不能兑现“已证明自然策略改进”的原强主张；恢复方案不承诺任何正向效果。
